# src/host/esp32 - the reconstruction on an ESP32-S3 (the LilyGO T-Deck Pro)

An ESP-IDF application, built with PlatformIO, that runs the reconstructed
Newton on the T-Deck Pro (`docs/host-tdeck-pro.md` is the investigation
and the plan).  **Milestone A**, where it stands: NewtonScript on the
board - the ROM's objects mapped from flash as a baked image, the object
system, every area's natives, and the NewtonScript prompt on the USB
serial port.  The OS's tasks are not started yet (milestone B: a FreeRTOS
task runtime, the flash store, then the panel, touch and keyboard).

## What is here

| File | What |
|---|---|
| `platformio.ini` | the build: `espressif32@6.5.0` (ESP-IDF 5.1), the DevKitC-1 board with 16 MB of flash, `upload_speed` 115200 (the board's own USB port has no baud rate, and esptool's change of it failed) |
| `sdkconfig.defaults` | quad PSRAM (not octal, whatever LilyGO's README says), `malloc` reaching it, the USB serial/JTAG console, quad flash at 80 MHz, a 64 KB data cache with 64-byte lines, C++ exceptions and RTTI, `-O2`, no task watchdog |
| `partitions.csv` | the program (6 MB), the baked ROM objects (`objects`, 6 MB at 0x610000), the store (`store`, the rest - not used yet) |
| `upload_objects.py` | writes `objects.baked` (or `NEWTON_BAKED_IMAGE`) to the `objects` partition with every upload |
| `main/CMakeLists.txt` | the one component: the tree's sources with the desktop's flags (`forQ`, `host_compat.h` first, `-fwrapv`, `-fsigned-char`, `-falign-functions=4`), each source with its own include directories as `-iquote` |
| `main/newton_sources.cmake`, `main/forwarded/` | generated by `tools/tdeck/idf_sources.py` (below) - regenerate, don't edit |
| `main/esp32main.cpp` | the board's side (ESP-IDF's headers only): the console made a blocking stdio stream, the `objects` partition mapped, a 96 KB task for NewtonScript |
| `main/newtonmain.cpp` | the Newton's side (the DDK's headers only): the kernel heap (3 MB, in PSRAM), the baked objects, `InitObjects`, `RegisterAllNatives`, the REP; `DeviceMilliseconds()` and `DeviceMemory()` for NewtonScript |
| `main/esp32runtime.cpp` | the task runtime's entry points for milestone A: one task, so a system call never switches |

`hal/host/System.cpp` has an `ESP_PLATFORM` branch (its stack bounds from
FreeRTOS); everything else is the tree as the desktop builds it.

## Building and running

Everything comes from PlatformIO (`~/.platformio`); on Linux and macOS
`penv/bin/` for `penv/Scripts/`.

1. **The source list**, when sources have been added to or taken from the
   tree: from a 32-bit build's compile commands (the desktop's per-library
   include directories and flags are what it copies):

        cmake -G Ninja -S src -B tmp/build-arm -DCMAKE_TOOLCHAIN_FILE=$PWD/src/cmake/zig-arm-linux.cmake \
            -DCMAKE_BUILD_TYPE=MinSizeRel -DCMAKE_EXPORT_COMPILE_COMMANDS=ON \
            -DNEWTON_HOST_NEWTONSCRIPT=$PWD/build/host/host/newtonscript.exe
        python tools/tdeck/idf_sources.py tmp/build-arm/compile_commands.json

2. **The program**: `~/.platformio/penv/Scripts/pio run -d src/host/esp32`
   (the first build installs ESP-IDF - see tools/tdeck/README.md; after
   that about 20 s for a change, a few minutes for everything).

3. **The baked ROM objects** (`frames/ROMImport.h`): made by the 32-bit x86
   build (`src/cmake/zig-x86-linux.cmake`, run under WSL 2 or Linux; its
   layout is the ESP32-S3's) at the address the board maps the `objects`
   partition at - which the board prints when it starts ("the objects
   partition mapped at 0x3caa0000"):

        tmp/build-x86/host/newton --objects build/host/romsrc-objects.bin \
            --bake-objects src/host/esp32/objects.baked --bake-base 0x3caa0000

   A board given an image baked elsewhere, or by a build of another layout,
   says so and starts without the ROM's objects.  Bake again whenever the
   object file or the frames layout changes.

4. **Onto the board**: `~/.platformio/penv/Scripts/pio run -d src/host/esp32 -t upload --upload-port COM4`
   - the program and, when it is there, `objects.baked`.  If esptool stops
   with "No serial data received" after the stub starts, the board needs
   power taken off it (the USB cable out, the battery out) and back.

5. **The prompt**: any serial terminal on the port, or from a script:

        ~/.platformio/penv/Scripts/python tools/tdeck/serialcapture.py COM4 60 --reset \
            --send "2 + 3;" --send "DeviceMemory();"

## What it measured (2026-10-11, the owner's V1.0)

- The program is 2.76 MB; 128 KB of the internal RAM and 5 MB of the
  PSRAM are free with the REP running.
- Start: the baked objects in 11 ms (mapped, not read), the object system
  in 0.7 s, the natives in 1.1 s.
- NewtonScript (`DeviceMilliseconds`): a 100,000-pass integer loop 437 ms;
  2,000 strings made and stored 979 ms; 2,000 integers made and sorted
  49 ms - about 120, 500 and 80 times the 32-bit desktop build's time on
  the development machine.  The processor alone accounts for most of the
  first and last; the allocation-heavy one is the PSRAM's cache misses
  (docs/host-tdeck-pro.md).
