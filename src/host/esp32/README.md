# src/host/esp32 - the reconstruction on an ESP32-S3 (the LilyGO T-Deck Pro)

An ESP-IDF application, built with PlatformIO, that runs the reconstructed
Newton on the T-Deck Pro (`docs/host-tdeck-pro.md` is the investigation
and the plan).  **Milestone B**, where it stands: the OS booted on the
board - the ROM's objects mapped from flash as a baked image, the kernel
and its tasks on FreeRTOS, the newt world with a 240x320 one-bit display
**on the e-paper panel**, **the touch panel as the pen and the keyboard as
the keyboard**, and the store in RAM - with a NewtonScript prompt on the
USB serial port, each line evaluated in the newt world.  Next: the flash
store.

## What is here

| File | What |
|---|---|
| `platformio.ini` | the build: `espressif32@6.5.0` (ESP-IDF 5.1), the DevKitC-1 board with 16 MB of flash, `upload_speed` 115200 (the board's own USB port has no baud rate, and esptool's change of it failed) |
| `sdkconfig.defaults` | quad PSRAM (not octal, whatever LilyGO's README says), `malloc` reaching it, task stacks allowed in it, the USB serial/JTAG console, quad flash at 80 MHz, a 64 KB data cache with 64-byte lines, C++ exceptions and RTTI, `-O2`, no task watchdog, a 1 ms tick |
| `partitions.csv` | the program (6 MB), the baked ROM objects (`objects`, 6 MB at 0x610000), the store (`store`, the rest - not used yet) |
| `upload_objects.py` | writes `objects.baked` (or `NEWTON_BAKED_IMAGE`) to the `objects` partition with every upload |
| `main/CMakeLists.txt` | the one component: the tree's sources with the desktop's flags (`forQ`, `host_compat.h` first, `-fwrapv`, `-fsigned-char`, `-falign-functions=4`), each source with its own include directories as `-iquote` |
| `main/newton_sources.cmake`, `main/forwarded/` | generated by `tools/tdeck/idf_sources.py` (below) - regenerate, don't edit |
| `main/esp32main.cpp` | the board's side (ESP-IDF's headers only): the console made a blocking stdio stream read by a task of its own into a queue of lines, the `objects` partition mapped at 0x3d000000, the Newton's tasks' threads (FreeRTOS tasks with 48 KB stacks in PSRAM, all on core 1) |
| `main/tdeck_panel.cpp` | the panel (a task on core 0): the display's grays watched and sent to the UC8253 once a change settles - a partial refresh (0.65 s) over the rectangle that changed, a full one (3 s, flashing) for a new page and to clean up after 30 s still; how the controller has to be driven, and how that was found, is its header's; settings changed while it runs: `DevicePanelSet(name, value)` |
| `main/tdeck_input.cpp` | the CST328 touch panel and the TCA8418 keyboard (a task on core 0, a hundred times a second) into the window shims every host's window calls (`HostWindowPenDown/Move/Up`, `HostWindowKey`, host/HostKeyboard.cpp); the owner's keyboard layout (Shift, Sym's symbols, Alt's navigation keys or the Command key) |
| `main/newtonmain.cpp` | the Newton's side (the DDK's headers only): the kernel heap (3 MB, in PSRAM) with a 1 MB NewtonScript heap, the baked objects, the newt world configured (240x320x1, the store in RAM) and the OS booted; the kernel services task hands each console line to the newt world as a `'host/'eval` event, whose handler evaluates it and prints the result; `DeviceMilliseconds()`, `DeviceMemory()` and `DevicePanelSet(name, value)` for NewtonScript; every NewtonScript throw printed with its script stack (`NEWTON_TRACE_EXCEPTIONS`, set there) |

The tree's own platform code has `ESP_PLATFORM` branches where it must:
`os600/kernel/host/TaskRuntime.cpp` (a task's thread is a FreeRTOS task
the board's side makes), `hal/host/System.cpp` (the stack's bounds from
FreeRTOS; a reset prints a backtrace), `hal/host/HostSockets.cpp` (lwIP:
no interface list, no reverse lookup, no signals).  `malloc(0)` answers a
block, as the desktops' do (newlib's answers nil; `__wrap_malloc` in
esp32main.cpp).  Everything else is the tree as the desktop builds it,
host/HostKeyboard.cpp included (the key queue and the window's shims;
the kernel services task sends the keys with `HostKeyboardSendKeys`).

## Building and running

Everything comes from PlatformIO (`~/.platformio`); on Linux and macOS
`penv/bin/` for `penv/Scripts/`.

1. **The source list**, when sources have been added to or taken from the
   tree: from a 32-bit build's compile commands (the desktop's per-library
   include directories and flags are what it copies):

        cmake -G Ninja -S src -B tmp/build-arm -DCMAKE_TOOLCHAIN_FILE=$PWD/src/cmake/zig-arm-linux.cmake \
            -DCMAKE_BUILD_TYPE=MinSizeRel -DCMAKE_EXPORT_COMPILE_COMMANDS=ON \
            -DNEWTON_HOST_NEWTONSCRIPT=$PWD/build/host/host/newtonscript.exe
        python tools/tdeck/idf_sources.py tmp/build-arm/compile_commands.json

2. **The program**: `~/.platformio/penv/Scripts/pio run -d src/host/esp32`
   (the first build installs ESP-IDF - see tools/tdeck/README.md; after
   that about 20 s for a change, a few minutes for everything).

3. **The baked ROM objects** (`frames/ROMImport.h`): made by the 32-bit x86
   build (`src/cmake/zig-x86-linux.cmake`, run under WSL 2 or Linux; its
   layout is the ESP32-S3's) for the address the board maps the `objects`
   partition at, 0x3d000000 (`esp32main.cpp`'s `MapObjects`: ESP-IDF
   would put it after the program's own mappings and the PSRAM's, which
   move as the program grows, so the space below 0x3d000000 is filled
   first - 4 MB of room for the program to grow in):

        tmp/build-x86/host/newton --objects build/host/romsrc-objects.bin \
            --bake-objects src/host/esp32/objects.baked --bake-base 0x3d000000

   A board given an image baked elsewhere, or by a build of another layout,
   says so and starts without the ROM's objects.  Bake again whenever the
   object file or the frames layout changes.

4. **Onto the board**: `~/.platformio/penv/Scripts/pio run -d src/host/esp32 -t upload --upload-port COM4`
   - the program and, when it is there, `objects.baked`.  If esptool stops
   with "No serial data received" after the stub starts, the board needs
   power taken off it (the USB cable out, the battery out) and back.

5. **The prompt** ("the OS is up", about a minute after the start): any
   serial terminal on the port, or from a script:

        ~/.platformio/penv/Scripts/python tools/tdeck/serialcapture.py COM4 120 --reset \
            --after "the OS is up" --send "2 + 3;" --send "DeviceMemory();"

   PlatformIO does not notice that `main/newton_sources.cmake` changed:
   touch `main/CMakeLists.txt` after regenerating it.  For a heap that
   seems damaged, `CONFIG_HEAP_POISONING_COMPREHENSIVE=y` in
   `sdkconfig.defaults` (delete `sdkconfig.tdeck-pro` so that it is read
   again) checks each block's ends when it is freed.

## The panel, touch and keyboard (2026-10-11)

The panel shows the Newton cleanly; typing and taps update only what
changed.  Settings (`DevicePanelSet`, while it runs; tdeck_panel.cpp lists
them): `trace` (each refresh's kind, time and rectangle on the console),
`bigChange`, `cleanAfter`, `partialTemperature`, `fullTemperature`,
`redraw`, `test` (a test pattern - tools/tdeck/panelprobe.py photographs
it), and the controller's set-up ones kept for comparing.  Touch arrives in
the panel's pixels; the Newton's own pen calibration takes out a finger's
offset.

## What it measured (2026-10-11, the owner's V1.0)

Milestone B (the OS booted):

- The program is 4.0 MB; 285 KB of the internal RAM is static data
  (87%), 29 KB is free with the OS up, and 2.6 MB of the PSRAM.
- Start: the kernel and its tasks in 10 s, the newt world in another
  17.5 s ("Welcome to NewtonScript!"), the OS up - `gNewtIsAliveAndWell`,
  the built-in applications installed - 62 s after the start.
- NewtonScript as fast as at milestone A (the 100,000-pass loop 445 ms);
  `GetRoot().viewBounds` is 240x320; one store.

Milestone A (NewtonScript alone):

- The program is 2.76 MB; 128 KB of the internal RAM and 5 MB of the
  PSRAM are free with the REP running.
- Start: the baked objects in 11 ms (mapped, not read), the object system
  in 0.7 s, the natives in 1.1 s.
- NewtonScript (`DeviceMilliseconds`): a 100,000-pass integer loop 437 ms;
  2,000 strings made and stored 979 ms; 2,000 integers made and sorted
  49 ms - about 120, 500 and 80 times the 32-bit desktop build's time on
  the development machine.  The processor alone accounts for most of the
  first and last; the allocation-heavy one is the PSRAM's cache misses
  (docs/host-tdeck-pro.md).
